# Android data component — build only

Candidate-only Java sources live in `src/org/momhealth/gateway/data/`. They do not alter the working release, BLE protocol, or device adapters. No tests, database operations, network requests, or device operations were executed in this task. Native Android API 36.1 compilation succeeded with Java 8 compatibility warnings.

## APIs and activation

- `HealthSample(...)` accepts sample/device/session UUIDs, model, live/history provenance, offset-aware receipt time, optional actual watch time, nullable HR, missing reason, and synthetic flag. Device IDs are opaque UUIDs. HR is 20–250 or absent; this is transport validation, not accuracy validation. No BP/glucose fields exist.
- `HealthStore(Context)` is lazy. `setRecordingEnabled(true)` is required before `append(sample)`. Consent defaults off for each instance/process. Caller must only append current confirmed-session values after explicit opt-in. `append` is idempotent for identical IDs/content and rejects collisions. Maximum 10,000 records; full capacity raises an error without eviction.
- `history(limit, beforeRowId)` returns newest first, maximum 100. Pass zero for first page and the last returned row ID for the next page. Entries retain device/session provenance. `pendingBatch(limit)` selects oldest pending records; `status()` returns pending/uploaded/failed counts and last attempt. These explicit operations open/create the local database.
- `clearAll()` and `deleteSample(id)` are explicit local deletion APIs. UI must confirm deletion, stop recording, and cancel any transfer before deleting. Nothing deletes automatically. App-private native SQLite is not independently encrypted; Android application sandbox/device encryption apply.
- `BatchUploader(url, allowLoopbackHttp)` requires an exact `/v1/batches` endpoint, HTTPS except explicitly allowed loopback HTTP, and no credentials/query/fragment. No redirects, auto retry, or scheduler. Request limit is 128 KiB, response limit is 256 KiB, and timeouts are 10 seconds. Platform cleartext policy remains applicable; this code does not change it.
- `SyncCoordinator.uploadOnce(store, uploader)` uploads at most 100 pending items explicitly and synchronously. Invoke only from the Activity-owned executor. Cancel at foreground exit using `uploader.cancel()` and interrupt/cancel the task. Create a fresh uploader for each later explicit attempt; cancelled instances cannot restart.
- ACK parsing rejects mismatched batches, repeated or unsolicited IDs. Accepted/duplicate IDs become uploaded in one local transaction only after a parsed successful server response. Rejected/missing IDs remain pending. Timeout/cancellation may occur after server commit; later explicit retry relies on sample-ID idempotency. Server commit is a protocol promise, not something the client can independently prove.

## Unexecuted acceptance coverage

`tests/data/DataComponentChecks.java` provides callable source checks for validation, no-result provenance, duplicate collision, opt-in enforcement, partial acknowledgment, durable queue transitions, bounded history, explicit deletion and endpoint restrictions. It must only run against a disposable application context. It was not run.

Additional runtime checks to perform together later: process recreation retains records but resets recording consent; fill all 10,000 slots and confirm the next insert fails without deletion; SQLite rollback on disk-full; history pagination across multiple devices/sessions; delayed server commit then lost response and duplicate retry; malformed/oversized/redirect server responses; cancellation during connect/write/read; Activity exit during acknowledgment; no retry after failure without user action; disabled controls prevent concurrent upload/delete. These require Android and synthetic local server execution and remain unverified.

No real health data has been persisted or transmitted by this build work. Wire format follows `CONTRACT.md`; UUID-only device IDs are a deliberately stricter client subset of opaque identifiers. Upload requires separately configured server capability and appropriate authorization; no endpoint or credentials are provisioned here.

Non-synthetic populated HR is restricted to live V1/V8 observations. V4/history may carry nullable unavailable states, or explicitly synthetic fixtures, but cannot assert real populated HR. Both input and normalized UTC timestamp years must fall in 1–9999. Check source includes these boundaries but remains unexecuted.

The optional `BatchUploader(url, allowLoopbackHttp, bearerToken)` overload accepts an externally supplied memory-only token, validates token syntax/length (32–4096 characters), and sends it only to the original HTTPS endpoint. Redirects remain disabled. No credential is generated, configured, logged, or persisted. Mixed device/session batches retain every item's own identifiers; the client performs no cross-session aggregation. Cancellation and acknowledgment use one lock so cancellation before the acknowledgment transaction leaves the batch pending; cancellation after committed acknowledgment cannot undo server/local commit.

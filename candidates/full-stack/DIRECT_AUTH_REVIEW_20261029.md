# Synthetic Railway direct-authentication review

The existing application already authenticates caregiver reads with HTTP Basic credentials and phone writes with a distinct bearer token. It checks roles, paths and methods; forwarded headers do not establish the user's identity. This means direct application authentication is technically possible without adopting another provider. It does not make the current implementation ready for exposure: the gateway also fails closed unless the direct peer matches a configured trusted CIDR and the configured HTTPS-forwarding condition is met. Removing that gate changes the trust boundary; it does not authenticate the edge or prove an equivalent security control.

Railway documents HTTPS between client and public edge, then HTTP forwarded to the application container: https://docs.railway.com/guides/keycloak-authentication. Railway staff describe an encrypted WireGuard tunnel for edge-to-container transport: https://station.railway.com/questions/fastapi-uvicorn-trusted-proxy-configura-9c06fa12. Railway documents private networking isolated by project/environment, but services in one environment may communicate: https://docs.railway.com/networking/private-networking/how-it-works. Railway staff state there is no published proxy CIDR or signed edge header and that private-network calls bypass public edge sanitization: https://station.railway.com/questions/need-authoritative-client-ip-proxy-tru-090eac86. These facts do not authenticate a direct peer or prove a credential traversed the public HTTPS path. Application credentials themselves are bearer secrets and may be replayed if stolen.

An independently reviewed Railway-only synthetic design could explicitly treat the project/environment and its administrators as its trust boundary, rather than treating forwarded headers as identity. It would require a concrete implementation that protects credential confidentiality and rotation, strictly separates caregiver read and phone write permissions, protects normalized methods and paths, rejects ambiguous headers, safely handles errors, and provides effective abuse prevention without locking out every legitimate user in a role. Its security assumptions, testing and residual risks must be reviewed and accepted; an observed single-service state alone is not a continuously enforced guarantee. The current shared per-role limiter can deny service to legitimate users, and Railway's Under Attack Mode blocks non-browser clients: https://docs.railway.com/networking/waf. This is a possible alternative trust model, not a verified equivalent replacement or instruction to disable the existing gate.

The user already approved an internet-reachable synthetic test site and separate test credentials. Any revised security-sensitive trust model must be concrete and independently reviewed, with applicable approval and automatic review satisfied before exposure. Real health data and phone activation remain outside that approval. No external provider is inherently required; a signed-access/private-tunnel alternative and its additional provider, DNS, dependency, cost and credential decisions are separately documented in `backend/railway_candidate/INGRESS_THREAT_MODEL_20261029.md`. Neither design has been implemented or validated for public exposure.

Automatic approval review rejected creation of the existing Railway service's public domain because verified edge identity/proxy trust was missing. No domain was created, and no retry or indirect route was attempted. A new attempt requires materially relevant evidence and satisfaction of the review, not only user permission or an assumption about the peer address.

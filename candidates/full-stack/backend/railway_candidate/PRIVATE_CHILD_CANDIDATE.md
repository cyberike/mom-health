# Synthetic test: private child directory candidate

Explicitly opt-in code. The synthetic private-child self-test passed on Railway on October 29, 2026, and its compute was stopped afterward. See [PRIVATE_VALIDATION_20261029.md](PRIVATE_VALIDATION_20261029.md). The default gateway and direct-mount self-test remain unchanged unless the new option is selected.

`MOM_HEALTH_PRIVATE_CHILD=true` selects a fixed `mom-health-private` child of the configured mounted volume, with database at `<mount>/mom-health-private/mom-health-synthetic.sqlite3`. The service must own the existing non-symlink mount and the mount must not be writable by group or other users; the code never chmods the volume root. It creates the child with mode 0700 only if absent; an existing child must be service-owned and private. POSIX directory-relative, no-follow opens protect the child/database path, and exclusive database creation refuses an existing file. Existing children or files are not altered or deleted on validation failure. The self-test can leave a newly created synthetic directory/database after interruption; inspect before retry.

The fresh synthetic self-test additionally refuses to enter any existing child, even if it appeared after inspection. This decision is made at atomic directory creation, and returns the fixed `CHILD_EXISTS` category. Ordinary non-test reuse still validates an existing child and database. The synthetic test must not automatically retry after creating a child or database; inspect the retained data first.

The earlier Railway diagnostic reported `PRIVATE_MODE=NO` without distinguishing 0755 from a group/world-writable mode. The subsequent read-only preflight reported no group/other write bits and no POSIX access or default ACL xattrs at that time; the synthetic test then passed with fd-based checks. `os.path.ismount` remains unsuitable for some bind mounts; no mount safeguards are bypassed. POSIX checks do not establish all platform ACLs, host capabilities, trusted-administrator behavior or protection against filesystem attacks by the same service UID. The database is later reopened by SQLite by pathname, so privileged or same-UID concurrent path replacement remains outside this candidate's guarantee. Do not enable publicly or for real data on this basis.

Verification includes Windows POSIX-operation model tests and the bounded Railway synthetic run detailed below. A read-only `wsl.exe --list --quiet` returned `Wsl/EnumerateDistros/Service/E_ACCESSDENIED`; it was not retried or bypassed. The passing Railway test exercises its current synthetic mount and fd-based ACL path; negative Linux filesystem cases, browser, device, public ingress and real-data behavior remain unverified.

## Follow-up review and Linux validation plan

The focused Windows mock suite now has nine passing tests. The added cases check descriptor cleanup on a failed child open and an existing database, the fixed permission-failure category, and rejection of existing databases with unsafe mode, owner, link count or file type. These are simulated POSIX calls, not evidence of Linux behavior. An independent read-only review confirmed the documented same-service-UID and privileged path-replacement limits.

Following the fresh-child race fix, 31 local tests passed: 10 private-child mock tests, 7 synthetic self-test tests, 4 supervisor tests and 10 gateway tests. They include refusal to enter an existing child, no overwrite if a database appears, and delivery of the fixed diagnostic category. POSIX filesystem behavior remains unverified by the Windows mocks.

The candidate rechecks `system.posix_acl_access` and `system.posix_acl_default` on the already-open mount directory file descriptor immediately before creating the child. Both must return `ENODATA`; a present ACL, unsupported xattr operation, permission error or other unknown outcome fails closed before creation. The check covers Linux POSIX ACL xattrs only; non-POSIX platform ACLs and changes by a trusted service user or administrator after the check remain outside its guarantee. Following this update, 32 local tests passed, including mocked access/default ACL present and unsupported/error cases. The October 29 Railway synthetic test passed with fd-based xattr access.

After that Railway run, the local candidate was further changed to check both ACL xattrs on the opened child before touching its database, including when reusing an existing child. A present or unreadable child ACL rejects access and closes both directory descriptors. The follow-up passed 35 local focused tests, including mocked child ACL cases; this newer source was not part of the Railway validation. Non-POSIX ACLs and changes by a trusted service user or administrator after checks remain outside the guarantee.

Desirable further validation on an authorized Linux environment would use a disposable test mount and synthetic data only. Verify the service-owned mount with both safe and group/other-writable modes; create a private child and exclusive new database; then repeat with a pre-existing database, symlink, incorrect owner or permissions, and multiple links. Check actual file modes, no-follow and descriptor cleanup, and verify that failures leave existing data unchanged. Inspect effective ACLs separately; mode bits alone do not establish ACL isolation. Test a mount that matches Railway's bind-mount characteristics, with its actual mount detection, without changing a real volume's permissions. Never treat these local checks as proof of Railway behavior. These negative cases have not been run on Linux; the October 29 Railway run was a positive synthetic test of the earlier source.

The October 29 preflight and synthetic test have now been completed. The synthetic child and database are retained as evidence; a fresh test must not overwrite or automatically reuse them.

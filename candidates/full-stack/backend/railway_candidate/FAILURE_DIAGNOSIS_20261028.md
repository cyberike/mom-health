# Private self-test failure: local diagnosis

Railway deployment 6aadcc00-7dbc-49f2-8cc2-ca978db17e81 remains CRASHED with restart policy NEVER. Read-only current metrics showed zero CPU and memory; sampled telemetry and CRASHED are not a guarantee of instantaneous billing cutoff. Retained 500 MB volume and evidence were not changed. No second cloud run occurred.

The build installed Python 3.13.16, FastAPI 0.162.0, Starlette 1.10.0 and httpx 0.28.1. Runtime recorded the container starting, volume mount and generic supervisor failure. The supervisor intentionally discarded child stdout and stderr, and the child caught errors under one generic message. Therefore these logs cannot distinguish import failure, mount/permissions, preexisting database, a failed check or timeout. The reported duration was shorter than 25 seconds, but timestamps do not identify the underlying failure. The original 20 staged files match the reviewed manifest. Build logs report image digest sha256:9541e3d2e08e36a89f0812632926c1ee27f59522cdd0125b0ce5457ca86f7073; this is a provider-reported build digest, not independent filesystem attestation.

The original generic failure was reproduced locally with the exact staged source and an intentionally unmounted fictional directory, without creating a database. This demonstrates a possible cause, not what happened on Railway. Railway's logs mention a bind mount; Python documents that os.path.ismount can fail to detect bind mounts on the same filesystem. Actual Railway mount metadata and permission bits are not known. Local Python 3.14/FastAPI 0.128/Starlette 0.50 differ from the deployed build, so compatibility differences are another unverified possibility. A separate restricted child in the local Windows installation failed to import a dependency from its disabled user site. It does not establish the remote failure cause.

The local candidate now emits only fixed status categories via numeric child exit codes; it does not relay child output, exception messages, paths, fixture values or credentials. Categories distinguish mode, path, prior database, mount, permission, storage availability, import, failed check, unexpected failure and timeout. Import failure means an ImportError during initialization, not proof a specific package is absent. STORAGE_MOUNT_INVALID may mean an undetected bind mount or a genuinely unsafe mount. The child environment excludes secrets and user PYTHONPATH; timeout remains 25 seconds. Unexpected supervisor errors are sanitized.

Independent review found and the local patch fixed a first-run race: the self-test requests atomic exclusive database creation, so concurrent starters cannot both reuse one database. The normal gateway retains its previous existing-database behavior. The 11 synthetic self-test/supervisor cases, including simultaneous start and no-overwrite, and 10 gateway regression cases passed. Review found no direct secret leak or fail-open in the diagnostic change. POSIX ownership/mount behavior is not validated on this Windows host.

The existing volume may contain a partially created synthetic database; its state is unknown. Do not overwrite, clear, or retry until it is inspected. A subsequent private diagnostic run requires separate authorization for another paid execution and an approved private way to inspect or handle any existing data. No public endpoint, real health data, phone action or cloud retry was used in this investigation.

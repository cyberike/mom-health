# Railway synthetic-only hosting candidate

This isolated wrapper leaves the existing backend and loopback default intact. It is a test candidate, not a production-ready health-data service. It uses only dependencies already declared by the backend. These source files do not themselves create secrets, account resources, a listener or a deployment. A separate finite in-process synthetic self-test has run on Railway; that result does not establish a hosted caregiver service or public access.

Start command (only after a separately approved deployment): `python -m railway_candidate.run` with Railway service root set to `backend`. The launcher validates configuration before listening on `0.0.0.0:$PORT`; proxy header rewriting by Uvicorn is disabled. The wrapper requires the direct socket peer to match explicitly configured private proxy CIDRs, and requires exact configured Host and `X-Forwarded-Proto: https`. **These checks do not establish TLS or isolate the origin.** An operator must verify Railway's ingress behavior, obtain a stable authoritative proxy peer range and confirm that untrusted peers cannot directly reach the origin or impersonate a trusted proxy. Railway documents proxy behavior at https://docs.railway.com/networking/public-networking/specs-and-limits. We do not treat client-supplied forwarded IP headers as an authenticated identity. No actual Railway proxy peer ranges are assumed; if verifiable ranges are unavailable this configuration cannot be deployed safely.

Synthetic-only configuration names (values must be supplied securely, not in command lines, files, URLs, or logs):

- `MOM_HEALTH_HOSTNAME`: exact lower-case HTTPS ingress DNS host.
- `MOM_HEALTH_CAREGIVER_USER`, `MOM_HEALTH_CAREGIVER_PASSWORD`: independent caregiver HTTP Basic credentials, with password 32-256 allowed ASCII characters. Entire dashboard HTML, JavaScript, CSS, and API reads require caregiver Basic authentication.
- `MOM_HEALTH_UPLOAD_TOKEN`: distinct bearer token for phone POST `/v1/batches` and `/v1/gateway-status` only; it cannot read the caregiver dashboard or API. Basic credentials cannot write these endpoints. Neither appears in URLs.
- `MOM_HEALTH_TRUSTED_PROXY_CIDRS`: comma-separated explicit CIDRs (1–16) matching directly connected ingress peers. Only RFC 1918 IPv4, IPv6 unique-local, or loopback ranges are allowed; link-local and documentation ranges are rejected. This is a peer allowlist, not proof of a genuine ingress; a broad private range may include untrusted callers. Do not choose or assume CIDRs until independently verified for this exact Railway service.
- `MOM_HEALTH_VOLUME_MOUNT`: absolute path to an existing mounted directory with no symlink path components. By default, on POSIX it must be owned by the service user with mode 0700 (or stricter). The application verifies it appears mounted using `os.path.ismount`; that check can fail to identify bind mounts, so a deployment that fails the check stays blocked and needs a reviewed alternative. Mount detection is not proof of durable storage, backups, encryption or external access control.
- `MOM_HEALTH_PRIVATE_CHILD`: absent or `false` uses the default direct-mount validation. The exact value `true` opts into the fixed private-child path; all other values reject startup. That path checks root ownership, group/other write permissions and root POSIX ACL xattrs before using an owner-private directory. Existing-child ACL protection and actual hosted reuse need separate verification; see `PRIVATE_CHILD_CANDIDATE.md`.
- `MOM_HEALTH_SYNTHETIC_DB_PATH`: with the default, exactly `mom-health-synthetic.sqlite3` directly inside the mount; with private-child opt-in, exactly `mom-health-private/mom-health-synthetic.sqlite3` inside it. The application rejects an existing symlink, non-regular file, multi-link file, or on POSIX a file not owned by the service user with mode 0600 or stricter. For an absent file it creates a new empty one with mode 0600; all database and journal files remain inside the private directory. The validation still requires the mount and directory to be controlled by trusted administrators: pathname checks are not a defense against a privileged concurrent filesystem attacker.
- `MOM_HEALTH_ALLOW_REAL_DATA` must be absent or `false`. Startup fails if it is `true`, and the internal backend rejects real samples unconditionally.

The private dashboard uses same-origin browser credentials for read-only API fetches; phone writes use the established bearer wire contract. Basic credentials can remain cached by a browser after the UI's Clear session action. There is no logout/revocation system beyond changing server credentials and restarting. Neither the dashboard nor backend has individual caregiver accounts or second-factor authentication.

An application-level limiter permits at most eight failed authentication attempts in each rolling 60-second window per role (caregiver and phone separately), then blocks **all** attempts in that role including valid ones until a failure expires, responding 429 with Retry-After. The hosted dashboard shows that wait in its message (checked through this gateway in `../dashboard/hosted-browser.test.js`). Requests without an Authorization header count as failures, and a browser makes such requests during every ordinary Basic sign-in (before the challenge on `/dashboard/`, and again on the first `/v1/` request). In a headless Chromium check on November 3, 2026 (`../dashboard/hosted-browser.test.js`), each fresh legitimate sign-in cost two failures and the fourth one within a minute was refused with 429; no wrong password was used. Reloads and repeated connects in an already signed-in browser cost nothing (ten in a row stayed 200). `direct_candidate.py` does not count requests that carry no Authorization header. No IP header or per-client identity is trusted. Memory use is fixed and the buckets are synchronized within one process. The limiter can be abused to deny service, resets after restart, and is not shared among workers, replicas or deployments. It does not rate-limit valid credentials, unauthorized unknown paths or traffic at the network edge. It is an additional local control, **not** comprehensive brute-force or volumetric-DoS protection. Require separately verified ingress-level abuse protection and one worker/replica before any public deployment.

**Do not deploy publicly until ingress rate limiting or equivalent brute-force protection, verified origin isolation/TLS, and storage access controls are in place and tested. Do not use real health data.** Additional unresolved work includes credential provisioning/rotation/revocation, protected backups, data retention, operational monitoring, independent review, browser QA, Android HTTPS end-to-end tests and actual infrastructure validation. The current code must be changed and reviewed separately to support real data; flipping an environment variable cannot turn that on.

From the `backend` directory, run `python -m unittest railway_candidate.test_gateway -v`. The tests use a loopback TestClient and fictional sample values, temporary test-only passwords and isolated synthetic SQLite; they start no listener or network service. They exercise private shell, separate read/write roles, duplicate header rejection, direct-peer CIDR checks, bad-origin rejection, bounded concurrent auth-failure limits, forwarded-IP spoofing, mocked mount validation and denial of real-data mode. Local tests mock mount detection; Windows cannot exercise POSIX owner/mode enforcement. They do not validate Railway ingress, direct-peer origin isolation, TLS, basic-auth browser behavior, actual volume mount, permissions, durability/backups, edge protection or mobile behavior.

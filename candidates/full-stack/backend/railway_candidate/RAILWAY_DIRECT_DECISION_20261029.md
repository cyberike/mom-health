## What changes in the trust boundary

The existing `gateway.py` requires a trusted direct-peer CIDR and a configured forwarded-protocol condition before authenticating the request. The proposed standalone direct-auth candidate instead authenticates each allowed route using a caregiver Basic credential or a separate phone bearer credential, without using forwarded headers to identify a caller or establish TLS. This is a different trust model, not proof of the original edge-identity requirement and not a change to the existing gateway's defaults.

For public access it would rely on Railway's public HTTPS edge, private environment, control-plane and the user's authorized project administrators. Railway documents TLS on its public entry point, encrypted WireGuard connections between services, and isolation between project environments. Services inside the same environment can contact one another. Railway's published behavior does not let the application cryptographically authenticate that a request arrived from the public edge. A same-environment caller can supply its own forwarding headers, but would still need a valid application credential under this design. A project administrator or someone who gains access to its service configuration may be able to view or replace ordinary test secrets or add a service; assess membership, secret handling and configuration change controls before any deployment. A single-service environment is a point-in-time condition, not an enforced assurance.

Provider sources: [public networking](https://docs.railway.com/networking/public-networking/specs-and-limits), [private networking](https://docs.railway.com/networking/private-networking/how-it-works), [TLS termination](https://docs.railway.com/guides/keycloak-authentication), and [Railway proxy trust clarification](https://station.railway.com/questions/need-authoritative-client-ip-proxy-tru-090eac86). These references describe platform behavior, not independent verification of this specific service.

## Security and operational limits

Separate caregiver and phone credentials and origin method/path rules limit what each credential can do; they do not stop a stolen bearer credential from being replayed during its validity. HTTPS protects transport to Railway's public edge, but the application has no verified edge identity. No real health data may be sent to this synthetic candidate, and a client-supplied `synthetic` flag is not evidence that a payload is fictional. Logs, URLs, reports and code must never contain actual credentials. Credential entropy and the user's secure, account-bound handoff are operator responsibilities.

The candidate's in-process failure limiter stores up to 512 keyed HMAC fingerprints of failed authorization values, with a new random in-memory key per process. After eight identical failures in 60 seconds it throttles that fingerprint; raw credentials are not used as keys. A valid credential is not blocked solely by failed attempts, but the 32-handler limit can still return 503 under load. The candidate bounds headers and reads each authenticated request body under a ten-second absolute deadline with a 131,072-byte cap before starting backend or database work. Local synthetic tests exercised 32 stalled or trickling bodies, timeout and recovery, oversized requests, disconnects, and cancellation while a worker proceeds. These tests do not establish real edge behavior or a comprehensive server deadline. Header receipt occurs before ASGI handling, and database work and response delivery are not covered by the body deadline; stalled work or output can still occupy all slots. Cancellation shields downstream processing so a handler slot remains occupied until that task ends, but the limit is not established as a bound on underlying database-worker lifetimes under every cancellation or shutdown condition. The failure limiter only slows repeated *identical* invalid values: an attacker can vary guesses, cause bounded-state eviction, consume authentication work, or spread attempts across workers or restarts. These controls are not a verified per-client limit, distributed protection, effective general brute-force protection or a volumetric DDoS defense. Railway's documented platform-level request limit is far too broad to be a login-guessing policy, and its [Under Attack Mode](https://docs.railway.com/networking/waf) blocks non-browser traffic. Further ingress abuse protection, server/edge deadlines and availability/recovery procedures remain unresolved.

The candidate's current and optional previous credential for each role need to be independent, high-entropy secrets. Each previous value has an absolute expiry and can overlap for at most seven days from configuration; revocation requires changing configuration and replacing/restarting the relevant process. The process rejects a wall-clock rollback during its lifetime, but the high-water mark is lost on restart and reliable system time remains a prerequisite. Basic authentication may remain cached in a browser. Verify rotation, clock handling, service restart and credential removal on the actual test environment before relying on them; never create, print or deliver real secrets as part of local tests. No credential rotation is proven instantaneous across replicas or edge caches.

# Synthetic direct-candidate SQLite limits

`budgeted_sqlite.py` is an opt-in repository for the separate local direct-authentication candidate. It does not change the original SQLite repository, gateway or Railway service. A future launcher must construct it only for the same path validated by the candidate's storage check and must not accept an untrusted caller's arbitrary repository; the injectable repository argument is a trusted test/development hook, not a security boundary.

By default each connection uses a 0.25-second SQLite busy timeout and a 2-second cooperative lifetime budget measured by a monotonic clock. Checks occur before the current trusted repository's `Connection.execute`, `executescript` and `commit`; SQLite's progress handler requests interruption during long-running virtual-machine statements. Invalid or backwards clock readings fail closed. The repository rejects any attempt to enable its real-data mode and inherits the existing synthetic batch gate.

The opt-in `require_existing=True` requires an absolute filesystem path and rejects Windows UNC/device-style paths. A Windows drive letter does not prove that the drive is locally backed. It constructs a `file:` URI with `Path.as_uri()` so path characters such as `#`, `%` and `?` cannot become query parameters, then uses SQLite `mode=rw` and `uri=True` to refuse creating a database that is absent at connection time. [SQLite URI documentation](https://www.sqlite.org/uri.html) distinguishes `mode=rw` from the creating `mode=rwc`. **This is not read-only:** SQLite may create journal or WAL sidecars and recover or modify an existing database while opening or performing transactions. The default `require_existing=False` retains existing behavior. This option does not make metadata validation noncreating; the separate composition must use a noncreating validator. It does not prevent an already-present path from being replaced or redirected by a trusted same-UID/privileged actor or symlink race, and it does not prove that a database contains only synthetic records. The actual SQLite connection and special-character filename checks passed on Windows; POSIX URI escaping was syntax-checked only and a Linux/Railway SQLite runtime check remains outstanding.

These are cooperative controls, **not a hard deadline**. Python work between checks, connection opening, filesystem stalls, a SQLite lock wait already underway, rollback/close and an already-started commit can exceed the budget. The progress handler is disabled for an already-started commit and restored afterward so that the candidate waits for its actual outcome. The existing repository's acknowledgments are generated only after commit returns. If a commit is durable but a later error prevents the response, the outcome is uncertain; retry the identical batch to obtain its idempotent receipt. The code does not enforce a general arbitrary-SQL sandbox: direct short `cursor.execute` or `executemany` calls can bypass connection prechecks, and `executescript` on a pending transaction may implicitly commit in SQLite legacy mode. The current trusted repository uses the checked connection methods and initializes through a fresh connection.

The 16 synthetic tests in `tests/test_budgeted_sqlite.py` cover lock contention and an HTTP 503 with no acknowledgment, retry and duplicate behavior, interrupted long write with rollback, expiry mid-batch, commit failure before a write completes, simulated error after a durable commit followed by an idempotent retry, a started commit no longer being cancelled by the progress deadline, the synthetic-only guard, and the opt-in existing-only path. The cursor limitation is explicitly tested. Fixtures use separate workspace-local synthetic databases; they do not touch the retained Railway volume or any phone data. These tests do not establish behavior under real I/O failure, network cancellation, actual Railway storage, power loss or PostgreSQL.

# Proposed synthetic ingress design: evidence and unresolved gates

Status: design only. The existing gateway remains fail-closed; no public domain, external identity provider, tunnel, credential or DNS change is created by this document. An automatic approval review rejected generating the Railway public domain because the gateway lacked a verified edge identity/proxy-CIDR trust mechanism. Do not retry that action or expose the same service through another path without resolving that rejection and obtaining the applicable approvals.

## Why the current gate remains closed

The current gateway uses an explicit direct-peer CIDR allowlist and exact Host and forwarded-protocol checks. A private address, a currently observed socket peer, or an `X-Forwarded-Proto` value is not proof of trusted Railway public ingress. Railway staff state that no published ingress CIDRs, authenticated edge-header or edge-only guarantee is offered and that callers in the same private environment can bypass the public edge. The environment currently containing one service is a point-in-time observation, not a continuously enforced cryptographic identity. Source: <https://station.railway.com/questions/need-authoritative-client-ip-proxy-tru-090eac86>.

Do not replace the peer gate with an assumed broad private CIDR, forwarded-header trust, or a single-service assumption and call it equivalent. The Railway [public networking specification](https://docs.railway.com/networking/public-networking/specs-and-limits) describes external TLS and proxy headers, but does not by itself prove origin isolation or authenticate an incoming request at the app. The reviewed 0.8.3 code has no signed-provider-assertion verifier.

## Design candidate: independently authenticated access assertions

One possible future design uses Cloudflare Access with separate caregiver and phone hostnames, Access applications and distinct audiences. This is a proposal for threat review, not an implemented, tested, approved or deployed solution. Cloudflare documents that the origin receives a signed application JWT in `Cf-Access-Jwt-Assertion` and must validate its signature; a present header or browser cookie alone is not sufficient. The token issuer and application audience must match fixed, operator-configured values. Cloudflare's signing keys rotate, so validated key retrieval, bounded cache lifetime and fail-closed key refresh are required. Sources: [Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/) and [Application token](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/).

**A valid JWT proves only that the configured issuer signed an unexpired authorization assertion. It does not prove this particular request traversed the Cloudflare edge.** A bearer JWT copied by an attacker can be replayed to a reachable origin until it expires; direct-origin access can also bypass edge controls and revocation checks. Preserve a separately reviewed origin transport/isolation control and existing application authorization until an independently reviewed design establishes equivalent or stronger protection. Do not disable the existing peer restriction merely because a JWT has been supplied. Access logging, token expiry, replay and revocation behavior must be tested rather than assumed.

For a future design review, Cloudflare documents that its Tunnel connector can require Access JWT validation before proxying. A tunnel is a new connector and network/security configuration and can expose an origin through a different route; it must **not** be installed, started, configured or used to evade the rejected Railway-domain action. Its account, outbound access, origin isolation, costs, terms and the exact application-to-connector trust boundary all remain unverified. Source: [Tunnel origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/).

## Role boundaries

- Caregiver: an Access application restricted to the approved human caregiver identity, with a distinct caregiver audience. Only dashboard/static resources and allowed read endpoints are authorized. Deny all writes and unknown routes. Validate a stable identity claim as well as audience; do not assume optional group claims are present.
- Phone: a different Access application and audience limited to a named service token under a Service Auth policy. Permit only the intended batch and gateway-status writes; deny dashboard and all reads. The Android client would need to send both Cloudflare service-token headers on each request and securely retain, rotate and revoke its credential. A Cloudflare service-token application JWT has a `common_name` for the client ID and an empty `sub`; do not interpret it as a human identity. Cloudflare's `strict_service_token_auth` is organization-wide and affects cookie and redirect behavior; read and review its actual setting, and obtain separately scoped approval before any change that affects the organization. Sources: [application-token claims](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/) and [strict service-token authentication](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/).
- `/v1/gateway-status` supports both read and write methods. Path-only access policy cannot establish role separation; verify method, normalized path, intended hostname and signed audience at the application boundary. Reject unknown methods, paths, multiple or malformed assertion headers, and ambiguous Host/authorization headers. Cloudflare documents that a more-specific application-path rule takes precedence without inheriting its parent policy; review every route and normalization case individually, rather than relying on a parent rule. [Application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/).
- Keep application-level role credentials and the synthetic-only backend gate until a separate review explicitly replaces them. The synthetic flag is client-provided and cannot itself prove a record contains no real information. No real health data or phone activation is approved by this design exercise.

## Fail-closed validation contract

Use an independently reviewed maintained JWT/crypto library, not hand-written signature verification. This workspace currently has neither PyJWT, Python `cryptography`, Authlib, python-jose, Node `jose`, nor jsonwebtoken installed. Selecting/installing a dependency, licenses, version pinning and vulnerability review require the applicable authorization and checks; no dependency was installed here.

Every request must pass all of the following before reaching a data route: exactly one bounded-size assertion header; an explicitly pinned `RS256` algorithm and suitable RSA verification key; a trusted signature; fixed issuer; the correct role-specific audience and application-token type; expiry/not-before and other required time checks against a reliable clock; and the correct human/service identity and method/path pairing. Require issuance time and enforce a reviewed, bounded maximum token lifetime and clock-skew policy; token expiry alone is not instant revocation. Do not accept `alg=none`, a symmetric-algorithm downgrade, attacker-supplied key URLs (`jku`/`x5u`) or an untrusted issuer/audience. Do not accept an unknown `kid`, duplicate `kid` entries in a key set, expired token, unavailable/untrusted key service, malformed key set, bad signature, stale credential or ambiguous headers. Never put credentials, bearer tokens or health values into logs, URLs, exceptions or reports.

Fetch signing keys only from a fixed, configured HTTPS issuer endpoint with certificate verification and no redirects. Bound network time, response size, concurrent refreshes and refresh frequency, including unknown-key attacks; enforce key rotation and removal without making an outage an allow condition. Cache policy must be independently reviewed for security and availability. The design must also specify how loss of provider access or revoked keys fails closed, the exposure window for already-issued replayable tokens, and how the phone buffers pending data without reporting a successful upload.

## Required evidence before any external test

1. Identify and review a transport/isolation method that does not bypass the denied action and actually prevents direct-origin policy bypass or otherwise meets a separately accepted security model. Establish exact DNS, TLS and origin certificate behavior, including encrypted end-to-end transport and certificate validation. No weakening of TLS verification to make a test work.
2. Confirm the user's Cloudflare account and an eligible managed or partial-CNAME domain, account access, chosen plan, applicable terms and costs. Cloudflare's public Access setup requires an active Cloudflare domain: [self-hosted public application](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/). A free tier may be available but the user's actual eligibility, domain costs, usage and any incremental charges are unverified; do not treat a $50 project budget as an automatic provider hard cap.
3. Obtain the precise required approvals for a new external provider, domain/DNS or network configuration, any connector/software and its permissions, persistent service credentials, secret handoff and retention. Confirm an account-bound secure delivery mechanism before generating a service credential; Cloudflare states a newly created service-token secret is displayed once. [Service tokens](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/). The previously approved Railway-only test credentials do not automatically authorize a Cloudflare account or token.
4. Implement and independently review the chosen verifier, roles, connection/rotation handling, phone changes and safe credential storage using licensed maintained dependencies. Separately establish an effective brute-force/rate-limit control for the caregiver and machine paths; the current process-local limiter is a limited backstop that can lock out a role, not a validated public abuse defense. Railway Under Attack Mode is not appropriate as the sole phone API protection because it challenges or blocks non-browser requests: [Railway WAF](https://docs.railway.com/networking/waf).
5. Run synthetic offline negative tests: absent/duplicate/oversized headers; unsigned, modified, malformed, expired and excessive-lifetime tokens; wrong issuer, audience, type, algorithm, key and identity; missing, duplicate, unknown, rotated and revoked key IDs; parallel unknown-key requests; JWKS redirects, timeout, malformed data or invalid certificate; caregiver write and phone read; method/path confusion; token replay/direct origin; retry/partial acknowledgment and no sensitive logs. Verify no device collection or outbound health upload.
6. Only after the earlier denial is resolved through the appropriate review, and with approved resources and cost, stage controls while the app is unreachable where supported. Perform real external synthetic HTTPS, origin-bypass and auth/authorization tests, with separate browser and phone-test participation as needed. Verify costs, termination/rollback and no real data before describing a public test URL as usable. Actual production data, backups, prolonged unattended behavior and medical accuracy are separate gates.

No claims of a verified hosted service are made by this design; no account or infrastructure action was taken.

An independent read-only review requested the explicit RS256 allowlist, duplicate-key and redirect rejection, refresh concurrency bounds, bounded lifetime/replay policy, and verification without silently changing the organization-wide strict service-token setting. These points are recorded above; the review does not establish a deployed or cryptographically tested implementation.

# Railway-only direct-authentication candidate: local test report

The separate `direct_candidate.py` factory is synthetic-only and is not a deployment entry point. It does not modify the original gateway or its default direct-peer restriction. Its final SHA-256 is `f2a20df80f7b38f987f06cbce60b4ca1d3c3903a45f5b04a5994187da8d3b881`.

The candidate authenticates the caregiver and phone with distinct credentials and method/path allowlists. Optional previous credentials have an absolute expiry and a maximum seven-day overlap; updates and revocation require a process configuration change/restart, and reliable time across restarts remains an operator requirement. Forwarding metadata is not used to determine identity, authorization or TLS, and is stripped before forwarding to the loopback backend. Duplicate security headers and ambiguous message framing are rejected. The backend's real-data gate remains disabled; a client-provided synthetic flag cannot prove data is fictional.

Authentication failures for the same exact invalid credential are tracked using a bounded, in-process HMAC-fingerprint table. It is not general brute-force protection: unique guesses, eviction, restarts and additional workers can evade it. A fixed in-process admission cap limits simultaneous handlers, and authenticated request bodies have a 10-second absolute read deadline and 131,072-byte cap before backend work. Slots are retained while cancelled downstream work completes. Slow headers before admission, stalled response sends, database worker stalls and distributed abuse remain outside those controls; they need separately reviewed provider/server defenses.

The independent in-process adversarial suite in `tests/test_direct_adversarial.py` passed 18 tests. The full backend discovery suite ran 90 tests with one POSIX-only test skipped. The tests cover role separation, forged and duplicate forwarding/security headers, path and framing ambiguity, old-credential expiry, clock rollback, repeated-failure bounds, synthetic real-marked rejection, body stall/trickle/oversize/disconnect behavior and cancellation while synthetic database work is blocked. They do not establish public TLS, Railway ingress, real browser, phone or deployed behavior. An independent source review found no authorization bypass in the tested routes and identified the unresolved limits above.

The decision document `RAILWAY_DIRECT_DECISION_20261029.md` describes the revised Railway project/environment and administrator trust boundary and has draft wording for a later user decision. That wording is explicitly not ready to present as an activation request until the outstanding abuse and deadline risks and review conditions are addressed. No site, new credentials, phone changes or real health-data transfer were activated. The existing public-domain action remains rejected by automatic approval review; this local candidate does not itself resolve the lack of verified edge identity and was not used to bypass that denial. The prior Library helper-discovery and ADB authorization blockers were not retried.

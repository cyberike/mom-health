# Local Caddy timeout experiment: preparation only

**Not authorized or executed yet.** This is a synthetic local HTTP/1 experiment, not a Mom Health deployment, HTTPS test, Railway ingress test, device test, or evidence that Caddy's limits work. No Caddy binary has been downloaded, validated or run in this preparation.

The template binds an explicit loopback HTTP site and forwards only to a second loopback port. It disables Caddy's admin endpoint, configuration persistence and automatic HTTPS **only for this isolated fictional fixture**; never reuse it for a public or health-data configuration. It selects HTTP/1, disables upstream proxy-from-environment, uses a fresh task-local storage directory, sets a five-second grace period, and proposes 2-second header, 3-second whole-body, 3-second whole-response and 5-second idle timeouts. The write timeout bounds the entire response, not merely idle writes; the values are test settings, not production recommendations. Sources: https://caddyserver.com/docs/caddyfile/options and https://caddyserver.com/docs/caddyfile/directives/reverse_proxy.

The template has not been parsed by Caddy 2.11.7. Current documentation may differ from that release. HTTP/2, H2C, Railway-to-origin behavior, edge identity, browser authentication, database work, transaction rollback and real phone behavior remain untested. A proxy timeout or client disconnect does not establish that a backend transaction stopped or rolled back.

Validation can provision modules or create files, so retain the isolated storage path and do not call it read-only. If validation fails, stop and record diagnostics; do not proceed on guessed syntax.
5. Start only the verified Caddy process with that config, using a hidden Windows process and retain its System.Diagnostics.Process handle. Set $caddyBinary and $caddyConfig to actual absolute paths inside this task; set $quotedConfig to a double quote, followed by $caddyConfig, followed by a double quote. Start it with: Start-Process -FilePath $caddyBinary -ArgumentList @('run', '--config', $quotedConfig, '--adapter', 'caddyfile') -WindowStyle Hidden -PassThru. Retain the returned process object in $caddyProcess.
6. In a try/finally block, run: python -B -m railway_candidate.caddy_synthetic_harness run --proxy-port 18081 --fixture-port 18082. In finally, refresh $caddyProcess, and if it has not exited, call $caddyProcess.Kill(), then $caddyProcess.WaitForExit(5000). Report termination as uncertain if the wait returns false. Use the retained process object, never a process-name-wide kill or caddy stop; the admin API is disabled and unrelated instances must not be touched. Forced proxy termination does not prove an upstream worker stopped or rolled back.

The harness starts its own fictional fixture listener on 127.0.0.1 and checks a random in-process readiness marker through the configured proxy before sending probes. It never launches or terminates Caddy itself. Teardown stops the fixture's serve loop, shuts down only its accepted sockets and bounds three individual joins at five seconds each; this is not one overall five-second deadline. Synchronous OS socket-close calls have no proven hard bound. A failure or timeout is reported as uncertain; an unfinished non-daemon handler could keep the process alive. The harness process must also be owned by the caller: if its termination is uncertain, terminate only that exact process through its retained handle. No guarantee is made that a stuck OS or Python worker will terminate automatically.

## Interpretation and limits

Header and body probes report closure-observed or inconclusive, accepting closure or a plausible timeout response only after a minimum elapsed time. A failure to observe closure is not proof of safety or insecurity; an arbitrary HTTP status is not timeout success. The stream fixture sends at most 128 MiB in bounded chunks while its client does not read. A peer-closed observation can be consistent with the write deadline but cannot prove the cause: OS buffering, connection failures, the proxy or fixture can also affect it. Record fixture state and a healthy post-test control; if the stream completes or buffers without observable backpressure, or causation cannot be determined, mark the write test inconclusive.

The prepared offline tests exercise rendering, loopback/path constraints, response classification and modeled fixture-owned shutdown; they do **not** run Caddy or open a listener. Caddy's real parsing, header/body deadlines, backpressure and shutdown remain unverified. Further tests for normal slow-but-progressing traffic and other HTTP versions require separate review; the whole-response deadline may interrupt legitimate slow responses.

Automatic approval review previously rejected the public Railway domain because the gateway lacked verified edge identity and proxy trust. This experiment does not resolve or bypass that rejection, and no public exposure or real-data transfer is authorized by it.

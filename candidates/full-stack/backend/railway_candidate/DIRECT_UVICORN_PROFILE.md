# Local Uvicorn profile for the synthetic direct-auth candidate

`direct_server_config.py` constructs a Uvicorn configuration for a **loopback-only local test**. Importing it or calling `build_local_config` does not bind a socket, start a service, read credentials, or change the existing Railway gateway. A test must explicitly start `uvicorn.Server`; the module has no deploy launcher. A public deployment is not authorized by this profile.

`direct_local_composition.build_budgeted_local_config` is a separate explicit composition for an existing **disposable synthetic** fixture. It uses `existing_only_storage.validate_existing_storage` before constructing `BudgetedSQLiteRepository` with that same path and `require_existing=True`; the direct candidate independently repeats the noncreating validation and rejects a missing, non-budgeted or mismatched repository. Neither validator calls `mkdir` or uses `O_CREAT`; SQLite `mode=rw` refuses to recreate a database that disappears after validation. Composition does not connect to SQLite, run migrations, bind a socket or start a lifespan. POSIX validation performs no-follow, ownership, mode and ACL checks, but its tests here are modeled rather than executed on Linux. Windows checks are for local synthetic fixtures only: a drive letter can be mapped to a remote filesystem and these checks do not establish ACL isolation. In both cases, a trusted same-UID process or administrator can replace paths after validation. Running the returned application's lifespan **will** initialize/migrate its database, may modify it and may create journal/WAL sidecars despite `mode=rw`. Never pass user data or the retained Railway evidence database. A path and client-supplied synthetic flag cannot prove content is fictional. Credential arguments remain in process memory and are not intentionally persisted or logged by the builder.

The profile was checked against the installed Uvicorn **0.40.0** help and `uvicorn.Config` signature, and is meant to be reviewed again if the version changes. It selects h11, one worker, no reload, no WebSockets, no proxy-header rewriting, no access log, no default Server or Date headers, a 64 concurrency setting, a 64 connection backlog, a five-second keep-alive timeout, a 30-second graceful-shutdown timeout and a 32,768-byte h11 incomplete-event buffer. `log_config=None` and critical-only Uvicorn logging do **not** guarantee that application code, exceptions or other configured loggers cannot leak data; inspect logging separately. The profile does not change or authorize access credentials.

## What the limits do and do not do

- Uvicorn checks its concurrency setting after h11 has parsed a complete request; it is not a cap on accepted sockets with incomplete headers. The operating-system listen backlog is a queue hint, not a hard cap on all established connections.
- `h11_max_incomplete_event_size` limits buffered **incomplete** h11 events. It is not an absolute elapsed header deadline or an independently verified limit for every complete header. The direct candidate separately checks the combined ASGI header bytes after parsing.
- The keep-alive timeout applies between completed requests, not while receiving initial headers or serving a response. The profile does not establish a maximum time to receive headers or send a response. The direct candidate independently applies a ten-second absolute body-read deadline and a 131,072-byte cap **after** authentication and ASGI admission.
- Graceful-shutdown timeout bounds Uvicorn's wait for graceful completion; cancellation is not proof that a running synchronous database worker stopped or rolled back. A response can be uncertain after disconnect/shutdown. Durable idempotent batch/sample retry and separate database limits remain necessary.
- A single worker and an in-process request limiter are not a distributed brute-force or volumetric denial-of-service defense. Process restarts reset process-local limiter state. No assertion in this profile establishes client identity, proves edge TLS, or protects an origin reachable from another service in the environment.
- `limit_max_requests` is intentionally not configured: with a single worker and a provider restart policy of `NEVER`, exiting after a count could simply stop service. A deployment must select and test a compatible lifecycle before adding any such recycling policy.

Railway documents a 32 KB combined public-header limit, 60-second HTTP/1.1 idle time **between requests**, five-minute body upload limit, and request transfer/no-transfer limits. The published specification does not establish a complete-header deadline for this service, and cannot be assumed to protect same-environment private callers. See [Railway public-networking specs](https://docs.railway.com/networking/public-networking/specs-and-limits).

## Supported alternatives and prerequisites

An independently managed reverse proxy may supply missing header and response timeouts; Caddy documents `servers` timeouts including `read_header`, `read_body` and `write`, along with `max_header_size`: [Caddy global options](https://caddyserver.com/docs/caddyfile/options). These are possible controls, not evidence of a tested proxy or authenticated Railway edge. No Caddy or Nginx binary was found on the current PATH, and Hypercorn/Gunicorn were not present in the current Python environment. Adding a proxy requires a separately authorized source/license and installation review, executable/configuration validation, deployment/supervision plan, and synthetic security and behavior tests. Do not add, start or expose one merely to bypass the rejected Railway domain action.

For a concrete future review, the official Caddy 2.11.7 release lists a Windows amd64 ZIP (`caddy_2.11.7_windows_amd64.zip`, SHA-256 `0a1edc0b799512051c57071ce0e798d3f2cf67dc98171366f1d2b326072e3b06`) and a Linux amd64 tarball (`caddy_2.11.7_linux_amd64.tar.gz`, SHA-256 `727b91701a392de6ebc5027509f548bf39979e5216340d0faed8fa5e69c84f8b`). The release includes signature and SBOM assets; verify the official publisher's signatures and assess modules/dependencies before use. Caddy's repository is Apache-2.0 licensed. Sources: [release assets](https://github.com/caddyserver/caddy/releases/expanded_assets/v2.11.7), [license](https://github.com/caddyserver/caddy/blob/master/LICENSE), [asset verification and installation](https://caddyserver.com/docs/install). Neither artifact has been downloaded or run. Approval to test a local Windows binary and any later Railway/Linux installation, configuration, network or public-exposure action are distinct decisions.

Before any actual hosting decision, independently verify the precise server, provider and origin trust boundary; effective ingress abuse controls; credential handoff, rotation and replay risks; availability under slow headers and stalled response/DB work; shutdown/retry behavior; resource limits and cost. Real health data and phone activation remain outside this synthetic profile.

## Local synthetic composition check

`tests/test_direct_composition_sqlite.py` creates a unique disposable workspace SQLite fixture, stubs mount recognition, constructs the budgeted composition without a SQLite connection, then explicitly starts the test lifespan. It exercises synthetic ingest and caregiver read, exact batch replay, a held SQLite write lock returning 503, and successful retry and exact replay after that lock is released. Observed repository connections use the validated fixture path. This is real local SQLite, but the mount check is stubbed; it does not validate POSIX ACLs, Railway storage, device operation or network ingress. The existing fixture is retained for inspection; no user data or retained Railway volume is used.

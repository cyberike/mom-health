# Private, bounded synthetic self-test

This is prepared locally, not deployed. `python -m railway_candidate.selftest_supervisor` starts one synthetic child with a 25-second subprocess timeout. The child calls the gateway in process, creates a synthetic SQLite database only on the explicitly supplied private mount, and prints a sanitized result through the supervisor. It uses fictional fixture credentials and does not test actual configured credentials, browser sign-in, a real phone, Railway ingress, or TLS. Set `MOM_HEALTH_SELFTEST=1`, `MOM_HEALTH_ALLOW_REAL_DATA=false`, `MOM_HEALTH_VOLUME_MOUNT` and the matching `MOM_HEALTH_SYNTHETIC_DB_PATH`; the child intentionally receives no production secrets. Five local tests passed. Windows tests mock mount checks and do not prove POSIX storage ownership or Railway mounting.

Configure one replica, restart policy NEVER, zero overlap and verified CPU/memory limits before any approved execution. Confirm the actual deployment and compute stopped afterward; a success status alone is not proof. No public domain, SSH key or second service is needed for in-process test results. The application performs no intended external network operations, but this is not a network sandbox or a platform-enforced egress limit. Timeout kills/reaps the direct child once running; Python startup, process creation, child descendants, or OS-level uninterruptible operations are not bounded by a platform deadline. An interrupted run can leave a partial synthetic DB; inspect it rather than overwrite or delete it.

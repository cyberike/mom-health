# Direct candidate: availability evidence and decision

Status: a **local, synthetic candidate** for review. The existing gateway/default and Railway service have not been changed or exposed by this work. This report does not establish public readiness, edge identity, device behavior or authorization to activate the revised trust boundary.

## What was tested

The final combined local backend suite ran **129 tests, with one POSIX-only test skipped**. The focused suite passed **36 tests**, including a synthetic SQLite integration check. Five actual TCP tests ran only on `127.0.0.1` using fictional credentials and data: normal protected health access; a deliberately stalled request body producing 408 with the body deadline shortened for the test; 32 blocked synthetic repository workers preserving admission limits after client disconnect and releasing slots when work completed; the effect of 63 incomplete headers on Uvicorn's 64-connection gate; and a stalled synthetic streaming response. These tests do not represent real Railway edge, real database I/O failure or phone/network acceptance.

Two findings remain concrete: a first incomplete request header stayed open longer than the configured five-second keep-alive time and later succeeded; and an active streaming response with a non-reading client remained stalled longer than that keep-alive time. This is consistent with the installed Uvicorn 0.40.0 h11 implementation: its request concurrency check happens after complete headers, and the keep-alive timer applies between completed requests, not while initially reading headers or writing an active response. The OS listen backlog is not a cap on all established sockets. Railway documents a 32 KB public-header limit, request transfer/inactivity limits and a body-upload limit; it does not thereby establish a verified shorter first-header or response-write deadline for this service or private callers. [Railway public-networking limits](https://docs.railway.com/networking/public-networking/specs-and-limits)

The candidate code separates caregiver-read and phone-write authentication, ignores forwarding fields as identity, limits authenticated bodies to 131,072 bytes and a ten-second absolute read interval before database work, and limits in-process request admission to 32. Cancellation retains an admission slot until its downstream task completes. These are process-local protections, not a guarantee against malicious traffic or permanent worker stalls. `direct_server_config.py` describes a separate **loopback-only** test profile: one Uvicorn worker, 64 concurrency setting, 64 backlog hint, five-second keep-alive, 30-second graceful shutdown, 32,768-byte h11 incomplete-event buffer, proxy-header rewriting and access logs disabled. It does not start a server by itself and cannot authenticate Railway's edge.

## SQLite and retained-data safety

`budgeted_sqlite.py` provides an opt-in synthetic repository with a 0.25-second SQLite busy timeout and a two-second cooperative statement/connection budget. Thirteen reported synthetic tests cover lock contention, interruption of a long write, rollback, commit failures, ambiguous post-commit failure and idempotent retry. The budget is **not** a hard deadline for opening a file, arbitrary Python or filesystem stalls, rollback, or a commit already in progress. The progress handler is disabled while commit/rollback runs; the code waits for commit to return before acknowledging. If the commit succeeded but the reply was lost, retrying the identical batch recovers its persisted receipt. The generic `executescript`/cursor limitations are documented in `SQLITE_BUDGETED_CANDIDATE.md`.

`direct_local_composition.py` uses the new noncreating `existing_only_storage.py` validator twice and constructs the budgeted repository for the same validated path with SQLite `mode=rw`. This mode refuses to recreate the main database if it disappears after validation; neither validation intentionally creates a file or connects SQLite. Constructing the configuration does not bind a socket or run migrations. It is **not a hard read-only guarantee**: opening a file can update access metadata, and starting the returned app's lifespan can modify the fixture and create SQLite journal or WAL sidecars. A trusted same-user process or administrator can still replace paths between validation and SQLite's pathname reopen.

The Windows checks are for disposable synthetic fixtures: a drive letter may be mapped to a remote filesystem, and the checks do not establish Windows ACL isolation. POSIX no-follow, owner, mode and ACL cases were modeled locally; those negative tests were not executed on Linux. Never use the retained Railway evidence database or real health data for this composition. A separate local integration test uses an actual disposable SQLite database and stubs mount recognition; it exercised synthetic ingest, caregiver read, batch replay, a held write lock returning 503, and successful retry. It does not establish real mount, Railway storage or network behavior.

## Concrete remaining decision

The reviewed Uvicorn-only profile is runnable for a private local test, but it has no built-in first-header or active-response write deadline. A separately managed proxy is one supported way to add those controls. Caddy documents `read_header`, `read_body`, `write` and keep-alive timeouts: [Caddy server options](https://caddyserver.com/docs/caddyfile/options). No Caddy or Nginx command was found on the current PATH, and no Caddy executable was found in the Mom Health workspace. To test this option, obtain specific authorization to download and run a verified official Caddy binary **inside the task workspace**, use a synthetic loopback fixture and preserve all existing files; review its source, signature, hash, license, configuration and process teardown. A later Railway/Linux install, configuration or exposure would be a separate decision. No binary has been downloaded or run for this proposal.

A local Caddy test would address only its tested connection/deadline behavior. It would **not** authenticate Railway's edge or resolve the earlier automatic-review rejection of the public domain. Before seeking exposure, the revised Railway environment/administrator trust model, secret handoff/rotation and origin access must be reviewed and the specific domain action must pass automatic approval. No real health data or phone activation is authorized by this report.

Stolen bearer credentials remain replayable and distributed attacks cannot be ruled out for a normal web service. Practical mitigations include high-entropy independent secrets, limited role/path permissions, rotation and revocation, access monitoring, sensible connection limits, incident response and suitable ingress protections. The existing fingerprint limiter only throttles repeated identical invalid values; it does not establish comprehensive guessing or denial-of-service protection. Any public synthetic test would require an explicit, reviewed acceptance of the resulting residual risks rather than a claim of perfect security.

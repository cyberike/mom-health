# Hosted backend candidate: same-host HTTPS proxy

This directory contains a proposed configuration, not an active service or production readiness claim. The application still listens on 127.0.0.1:8765 and ignores proxy headers at the server level. Caddy on the same machine is the only network-facing service in this design; it must terminate HTTPS and overwrite Host and X-Forwarded-Proto before forwarding to loopback. The app verifies those headers only after rejecting non-loopback peers. The loopback interface is a trust boundary: other local processes could imitate proxy headers and must be trusted/isolated. This design does not support a proxy on a different host or a platform that reaches the backend from a non-loopback address.

When explicitly configured, set MOM_HEALTH_HOSTED_HOSTNAME to an actual lowercase DNS hostname on both processes, MOM_HEALTH_ACCESS_TOKEN to a separately provisioned strong token, and set a durable private MOM_HEALTH_SQLITE_PATH or an approved PostgreSQL connection. No token is generated or provided by this project. The candidate Caddyfile sends the exact configured host and `https` scheme upstream. The HTTPS proxy must have a valid trusted certificate and must be the sole reachable ingress; do not expose the loopback API port. Default MOM_HEALTH_ALLOW_REAL_DATA is false. Hosted mode refuses to start without a token even for synthetic testing. The dashboard shell is public but has no records; all API calls require the token. This is single-principal bearer-token access, not individual caregiver accounts or device-scoped roles.

Before any real-data use: verify actual proxy behavior/TLS and host handling; add and verify authentication abuse protection at the ingress, strong secret provisioning and rotation/revocation, data-at-rest/backup/retention protections, monitoring and access control on the host, database durability, and the user's explicit activation decision. The Caddyfile does not implement request-rate limiting. PostgreSQL requires its driver and a separately tested server; neither has been installed or started here. A synthetic-only deployment can be tested first without uploading real records.

Tests: from backend run `python -m unittest discover -s tests -v`. Hosted configuration/origin and authorization tests use FastAPI TestClient and synthetic data. They do not launch or validate Caddy, TLS, a real browser, network transport, phone upload, PostgreSQL, firewalling, or deployment.

## Latest local verification

The recovered hosted-mode source was reviewed and exercised with 22 passing backend tests. Tests include duplicate `Host`, `Authorization`, and `X-Forwarded-Proto` rejection to avoid ambiguity at the application boundary. They use a synthetic fixture token only and an isolated SQLite database; no actual credential or listener is created. Caddy was not found among installed commands, so its configuration has not been syntax-checked or run. The proxy remains a proposal requiring its own review and real TLS/network acceptance.

The proposed topology requires one host that runs both processes: the API stays bound to loopback and Caddy terminates HTTPS there. A remote proxy or ordinary managed hosting platform forwarding from a non-loopback peer will be rejected by the current boundary. Do not silently trust a remote forwarded address or expose the API port to work around this. Selecting a suitable host, an ingress hostname and certificate, durable storage, and caregiver-managed credential provisioning/rotation is necessary to make the proposal deployable. Until those are selected and an operator explicitly approves activation, this file is not an instruction to deploy or send health data.
